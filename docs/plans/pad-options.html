RIPPS2 / PADEMU proposal

Any USB pad from a .pad file

PADEMU only knows a few Sony IDs today. Copy pads, like a DS3 knockoff with the ID 2563:0575, get ignored. The idea from the OPL help channel is to describe a pad in a human-readable text file, so anyone can add one without rebuilding anything. Here are three ways to do it, weighed against each other.

User flow (same in every option)

Mockups of the RIPPS2 screens, in order. The user holds a working pad (PS2 pad or a known DS3/DS4) to drive the menu, and presses buttons on the new USB pad when asked. With no other pad, the new pad itself drives the menu once a button is learned, and waiting 3 seconds skips a step.

Is it more inclusive than PADEMU ever was?

Yes, by a lot. Today PADEMU's USB side accepts exactly five IDs: DualShock 3, DualShock 4 (two models), and the PS3 Guitar Hero and Rock Band guitars. Anything else is ignored, even if it was sold for the PS3. With .pad files, any pad that sends ordinary USB HID input works once someone sets it up, and every setup is shareable.

Newly covered

  • Third-party PS3 and PS4 pads, wired or with a dongle (sushi's 2563:0575 kind)
  • Generic USB pads, arcade sticks, fight pads, SNES-style pads
  • 8BitDo and similar pads in their DInput/PS mode
  • Per-game button swaps for every pad, a real DualShock 2 included

Still not covered

  • Xbox 360 and Xbox One pads: not HID, so not by .pad file alone. belek666's 2020 modularPademu branch has drivers for both, planned as a later step
  • Pads that need a secret start-up handshake, like the Switch Pro Controller in USB mode
  • Bluetooth: BT stays DualShock 3/4 only
  • USB 2.0 high-speed-only devices: the PS2's USB port is 1.1
  • Pressure-sensitive buttons: other pads give full pressure or none

Is it foolproof?

No setup that relies on people's own pads can be fully foolproof. But RIPPS2 can make every mistake harmless and easy to undo:

Built-in guards

  • Sony pads never read a .pad file, so a bad file can't break a DualShock 3 or 4
  • The PS2 pad in port 1 always works, in the menu and in games
  • The file is checked in the menu; a broken one is skipped with a message, never sent to the game
  • Rumble, lights and the start-up packet start Off, so copy pads don't freeze
  • The Test screen shows exactly what the game will get before saving

What can still go wrong

  • A pad that reports buttons differently in different modes (switch on the back) needs one file per mode
  • A shared file made from a different revision of the "same" pad may map wrong; Redo fixes it in a minute
  • Some games read pads in unusual ways, and PADEMU's existing limits there still apply
  • Only testers with real pads can confirm each model; PCSX2 can't test this
Recommended

A. The front end packs it, PADEMU reads it

RIPPS2 reads PADS/*.pad before a game starts. It packs them into about 180 bytes and hands that to PADEMU along with the settings it already gets.

  • No card or file access needed inside the game
  • Works from any device the ELF boots from (MC, USB, HDD, MMCE)
  • A bad file gets caught in the menu, not mid-game
  • Touches three parts: the menu, ee_core and the IRX
  • Only launchers that adopt the packing step can use the files
Option B

B. PADEMU reads the .pad file itself

The IRX opens mc0:/PADS/ when it loads, as suggested in the thread, and applies whatever it finds there.

  • Every launcher that ships the IRX gets it for free
  • Smallest change on the front-end side
  • The game owns the card and IOP memory at that point. Reading files there risks hangs, and RIPPS2 has a history of those
  • Only covers MC0, not USB, HDD or MMCE
  • Adds a file reader to an IRX that has very little room
Option C

C. Read the pad's own description

Every USB HID pad reports its own button and stick layout (its HID report descriptor). PADEMU parses that, the way SDL does on PC. A .pad file only fixes the button order.

  • Many pads work with no file at all
  • Covers keyboards, mice and pads in one go
  • Copy pads often describe themselves wrong (the face-button mix-up in the thread)
  • A descriptor parser is the biggest and riskiest job in IOP memory
  • Still needs the setup screen for the button order

Recommended path

Build A first. Its .pad format is plain text, so another launcher can read the same files later, and option C can be added afterwards as an "auto-detect" step that fills in a first draft for the setup screen. Testing a real copy pad needs hardware testers, because PCSX2 can't pass a random USB pad through to PADEMU.

Build handoff

The full build brief for RIPPS2, RiptOPL and OPL: how the .pad files upgrade PADEMU (the Sony pads become built-in definitions, so there is one code path instead of five special cases), the file format, which file each part goes in, the safety rules and the test plan.

Open handoff.md

To save it, open it and use your browser's Save, or copy the text into a file named handoff.md.

Example: 2563_0575.pad

# USB Gamepad (made by RIPPS2)
name=USB Gamepad
vid=2563
pid=0575
offset=0       # buttons start at byte 0 (a real DS3 starts at 2)
cross=b0.1     # byte 0, bit 1
circle=b0.2
square=b0.0
triangle=b0.3
l1=b0.4
r1=b0.5
l2=b0.6
r2=b0.7
select=b1.0
start=b1.1
dpad=hat2      # byte 2 is a hat switch
lx=a3
ly=a4
rx=a5
ry=a6
rumble=off     # copy pads often hang on the DS3 rumble packet
led=off

Per-game button swaps go in PADS/GAMES/SLUS_123.45.pad, written like cross=circle.
